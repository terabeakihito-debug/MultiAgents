# MultiAgents P2 要件ベースライン

更新日: 2026-09-18  
状態: Draft（実装契約として確定する前の要件整理）

## 1. この文書の位置づけ

この文書は、今回の会話で確認した MultiAgents の P2 要件を、実装・検証できる単位に整理したものです。

このリポジトリには「P2」という正式な既存フェーズ定義は確認できないため、ここでは P2 を次の段階として仮定します。

> ローカル環境で、人が最終的な権限を持ちながら、複数のタスクと複数のエージェントを安全に自律実行できる実用段階。

要件の確定、モデル・プロバイダーの利用可否、同時実行数、画像生成の対象範囲、Git 操作の権限は、人の承認を経て正式決定します。この文書自体は実装・デプロイ・Git 操作の許可ではありません。

## 2. P2 の目的

- タスクの内容に応じて、実行フローを選べるようにする。
- 実行前に、目的・範囲・完了条件・利用エージェント・モデルを確認できるようにする。
- エージェントとタスクを並列実行し、待ち時間を減らす。
- 各エージェントの状態、直近のイベント、質問、成果物を理解できるようにする。
- 固定時間で強制終了するのではなく、進捗・停止・再開を基準に安全に運用する。
- 変更・検証・レビューの根拠を確認してから、commit・push・PR 作成へ進める。
- 画面を目的別に分け、利用者が「次に何を押すか」を迷わないようにする。

## 3. 対象利用者と権限

### 3.1 人のオペレーター

タスクを作成し、要件を確定し、実行計画を承認し、質問に回答し、成果物を確認します。commit・push・PR 作成・将来の merge は明示的な人の承認を必要とします。

### 3.2 実行サービス

選択されたフローを実行し、隔離された作業領域、タスク状態、チェックポイント、イベント、成果物を管理します。エージェントに Git の最終権限を自動付与しません。

### 3.3 エージェントとプロバイダー

エージェントは Codex、Cursor、Claude などを想定します。利用可能なモデルはサーバー側の許可リストとプロバイダーの能力・認証状態から選択します。画面から任意の CLI 引数や未許可モデルを注入できないようにします。

### 3.4 P2 の範囲外

P2 は単一ユーザーのローカル運用を前提とします。複数ユーザーの遠隔共同編集、チーム権限管理、公開 SaaS 化は別フェーズです。

## 4. 利用者の基本フロー

### 4.1 要件整理から実行する

1. 「新しいタスク」を開く。
2. エージェントと会話して目的、対象、対象外、完了条件を整理する。
3. 要件スナップショットを確認して保存する。
4. タスクの種類に応じたおすすめフローを確認する。
5. フロー、エージェント、モデル、並列実行、作業範囲を調整する。
6. 実行を開始する。
7. 進捗、質問、停止、チェックポイントを確認する。
8. 差分、検証結果、レビュー結果を確認する。
9. 人が承認した操作だけを実行する。

### 4.2 タスクの種類

| 種類 | 目的 | 推奨フロー |
| --- | --- | --- |
| バグ修正 | 原因の特定と回帰防止 | 調査 → 実装 → 対象テスト → レビュー |
| 機能追加 | 要件に沿った実装 | 要件整理 → 設計 → 実装 → 対象テスト → レビュー |
| リファクタリング | 挙動を保った構造改善 | 影響範囲調査 → 小分け実装 → 回帰検証 |
| 調査・セキュリティレビュー | 変更せずに判断材料を得る | 読み取り調査 → 独立レビュー → Findings |
| UI・ドキュメント | 表示・導線・説明の改善 | モック → 実装 → ブラウザ確認 → レビュー |
| PR レビュー・再作業 | 既存差分の確認と修正 | 差分読解 → 指摘整理 → 修正 → 再検証 |

おすすめは強制ではありません。タスクの種類、変更範囲、リスク、利用可能なエージェントを根拠として表示し、利用者が別のフローに変更できます。

## 5. 機能要件

### FR-01 要件整理の会話

実行前にエージェントと会話できます。会話から目的、対象、対象外、制約、完了条件、確認が必要な事項を抽出し、利用者が編集できます。

### FR-02 要件スナップショット

実行開始時に、要件、選択したフロー、エージェント、モデル、対象コミット、作業領域を不変のスナップショットとして保存します。実行後に要件が変わった場合は新しい版として扱います。

### FR-03 フローの推薦と選択

タスクの種類とリスクからおすすめのフローを提示します。固定の4ステップを前提にせず、利用者はステップの追加、削除、順序変更、スキップ条件を確認したうえで選べます。

### FR-04 条件付きフロー

差分の有無、変更ファイルの種類、テスト結果、レビュー指摘に応じて後続ステップを分岐できます。変更がない調査タスクに実装レビューを強制しない、UI変更にブラウザ確認を追加する、といった判断を行います。

### FR-05 エージェント・モデル選択

各ステップごとに担当エージェントとモデルを選択できます。画面には認証状態、利用可能モデル、利用枠、推奨理由を表示します。許可リスト外のモデルや任意の CLI コマンドは選択できません。

### FR-06 エージェントとタスクの並列実行

依存関係のないエージェントは並列実行できます。別タスクも同時に実行できます。各タスクは taskId に紐づく隔離状態と作業領域を持ち、他タスクの実行中表示や停止操作と混ざりません。

同時実行数は無制限にせず、初期値はローカル PC で最大2件を候補とします。CPU、メモリ、プロバイダー利用枠、作業領域の容量を見て待機列へ入れます。設定値はベンチマーク後に確定します。

### FR-07 進捗とイベント

エージェントごとに、フェーズ、状態、直近イベント、経過時間、利用ツール、変更ファイル、出力の有無を表示します。トークン数による見せかけのパーセント表示は採用しません。全体進捗と各エージェントの進捗を分けます。

### FR-08 一時停止・再開・キャンセル・質問

タスク単位で一時停止、再開、キャンセルを行えます。エージェントが判断できない場合はエラーではなく「人の回答待ち」に遷移し、質問と回答対象を表示します。ブラウザ切断後も、方針に応じて実行継続または再開可能な状態を選べます。

### FR-09 適応型の時間管理

通常運用で各ステップを一律の固定秒数で終了させません。代わりに次を組み合わせます。

- タスク全体の安全境界（設定可能な上限）
- プロバイダーのアイドル・無進捗監視
- 子プロセスの終了、停止、キャンセルの伝播
- 定期的なチェックポイント
- 再開時の未完了ステップの判定

「110秒を別の秒数に変える」ことは設計変更ではありません。タスクの規模、依存関係、実行状態に応じて必要な作業を待ち、停止した場合だけ安全に介入できる設計にします。

### FR-10 対象範囲に応じた検証

変更内容から検証を選びます。

- TypeScript変更: 型チェック、対象テスト
- API・サーバー変更: API・契約テスト
- UI・CSS変更: ブラウザ確認、アクセシビリティ確認
- 認証・権限変更: セキュリティ回帰テスト
- package.json・ビルド設定変更: 依存関係確認とビルド
- PR・最終承認: 必要な全体検証

毎回すべての重いテストを機械的に実行するのではなく、早い契約チェック、対象検証、PR 前の全体検証を分けます。

### FR-11 成果物とレビュー結果

タスクは、要件スナップショット、計画、変更ファイル、差分、検証結果、エージェント別の結果、意見の一致点、意見の相違点、未解決事項、最終判断を保存します。レビューが完了したことと、レビュー内容が存在することを別々に表示します。

### FR-12 人の承認と Git 操作

commit、push、PR 作成は、対象差分・検証結果・ブランチ・リモートを表示したうえで人が明示的に承認します。操作は冪等にし、二重実行を防ぎます。P2 の merge は「マージ可能」の判定と GitHub への導線を基本とし、アプリ内 merge は保護ルール、CI、監査ログを確認できる後続段階で追加します。

### FR-13 実行前チェックと利用枠

実行前に Node.js、npm、Git、依存関係、作業領域、CLI 認証、モデル利用可否、利用枠、必要な環境変数を確認します。未準備の場合は、対象タスク、原因、確認コマンド、再確認ボタンを同じ場所に表示します。

### FR-14 監査と再現性

入力プロンプト、要件版、フロー版、モデル、対象コミット、環境情報、イベント、出力、検証結果を関連付けます。あとから「どの条件で何が実行されたか」を確認できるようにします。

### FR-15 通知と外部状態

タスク完了、質問、停止、失敗、承認待ち、PR 状態変更を通知します。GitHub の PR・CI 状態はタスク画面から確認できるようにします。通知が未確認でも、タスク状態そのものを失いません。

### FR-16 画像・生成アセット

P2 では、画像生成を必須の実行プロバイダーにはしません。画像・スクリーンショット・生成アセットを要件と成果物として登録し、参照、保存、レビューできる境界までを対象候補とします。実際の画像生成プロバイダー、認証、コスト、著作権、保存容量、再生成は P3 の独立要件として判断します。

## 6. 状態モデル

推奨するタスク状態は次のとおりです。

```text
clarifying → planned → queued → running → validation → review → awaiting_approval
                         ↓          ↓          ↓             ↓
                      paused     waiting_for_human       recoverable

awaiting_approval → pr_open → ready_for_merge → completed
       └──────────────→ failed / cancelled
```

| 状態 | 利用者に見せる意味 | 主な操作 |
| --- | --- | --- |
| clarifying | 要件を会話で整理中 | 会話、要件編集 |
| planned | 計画と実行条件を確認中 | フロー・モデル変更、実行 |
| queued | 実行枠待ち | 優先度変更、キャンセル |
| running | エージェントが作業中 | 進捗確認、一時停止、質問への回答 |
| waiting_for_human | 人の回答・判断待ち | 回答、承認、停止 |
| paused | 利用者が一時停止 | 再開、キャンセル |
| validation | 対象検証中 | ログ確認、キャンセル |
| review | レビュー中 | 結果確認、再実行 |
| awaiting_approval | Git操作の承認待ち | 差分・検証確認、承認、却下 |
| pr_open | PR作成済み | CI・レビュー状態確認 |
| ready_for_merge | マージ条件を満たす | GitHubで確認、将来はアプリ内承認 |
| recoverable | 中断したチェックポイントから再開可能 | 再開、破棄 |
| completed / failed / cancelled | 終了状態 | 履歴・成果物確認、複製 |

## 7. 性能・運用要件の候補

以下は実装前の候補値です。実測後に正式な SLO として承認します。

| 項目 | 候補基準 |
| --- | --- |
| UI操作の受付 | 95パーセンタイルで1秒以内に受付表示 |
| タスク作成 | 作業領域作成を除き95パーセンタイル3秒以内。作業領域込みは10秒以内を候補 |
| 進捗イベント | 発生から画面反映まで95パーセンタイル1秒以内 |
| タスク一覧 | 100件を95パーセンタイル300ms以内に表示 |
| 再開 | 最新チェックポイントから3秒以内に再開状態を表示 |
| キャンセル | 子プロセス停止を確認し、通常10秒以内に状態を確定 |
| 並列数 | 初期候補は最大2タスク。CPU・メモリ・利用枠で動的に抑制 |
| 時間管理 | 固定のステップ上限を通常ルールにしない。タスク境界と無進捗監視を使う |
| 検証レーン | 軽量契約チェック、対象検証、PR前全体検証を分離 |
| 保存容量 | 出力・ログ・履歴の上限と保持期間を設定し、古い成果物を勝手に削除せず確認可能にする |

## 8. 安全性と非目標

- 作業はタスクごとに隔離された worktree で行います。
- レビュー担当は既定で読み取り専用とし、レビュー経路から commit・push を行えないようにします。
- API は localhost を基本とし、Host 検証だけを利用者認証の代替にしません。
- エージェントが自分で別エージェントを無制限に起動する再帰的な自律実行は P2 の対象外です。
- 任意のワークフロー DSL、任意のプロバイダーコマンド、未許可モデルの直接指定は P2 の対象外です。
- 自動 merge は P2 の既定動作にしません。ブランチ保護と CI を確認できる人の操作を残します。
- 失敗を「完了」と表示しません。正常完了、スキップ、質問待ち、停止、失敗を区別します。
- ブラウザ切断、プロバイダー切断、正常終了を同じエラーとして扱いません。

## 9. 受け入れ条件

1. 新しいタスクを開始すると、最近のタスク一覧に戻るだけでなく、要件整理または実行計画へ明確に遷移する。
2. 利用者は固定フローを押し付けられず、推薦理由を見て別フローを選べる。
3. 各エージェントの担当、モデル、状態、直近イベント、成果物を同じタスク内で確認できる。
4. 2つ以上の独立タスクを同時に実行しても、進捗、停止、成果物が混ざらない。
5. エージェントが質問した場合、画面はエラーではなく回答待ちとして次の操作を示す。
6. 長いタスクが固定ステップ時間だけを理由に失敗せず、無進捗の場合は理由と再開方法を示す。
7. UI変更にはブラウザ確認、API変更には対象テストなど、変更範囲に応じた検証が計画される。
8. 差分、テスト、レビュー内容、未解決事項を確認するまで commit・push・PR 操作を実行できない。
9. タスクを再開すると、要件、フロー、モデル、チェックポイント、既存成果物が復元される。
10. 日本語を基本にし、Codex / Cursor / Claude、モデル名、branch 名、コード識別子だけを必要に応じて原語で表示する。

## 10. 実装の段階案

### Phase A: 情報設計とモック

今回の `/p2-mock` のように、タスク一覧、要件整理、実行計画、実行状況、成果物と承認を画面として分離します。実データを変更せず、利用者テストで用語と導線を確定します。

### Phase B: ドメイン状態と API

要件スナップショット、フロー版、タスク状態、イベント、エージェント状態、成果物、承認を永続化し、状態遷移をサーバー側で検証します。

### Phase C: バックグラウンド実行と並列制御

タスクキュー、同時実行数、taskId 分離、キャンセル、チェックポイント、再開、無進捗監視を実装します。既存の固定ステップ予算はこの段階で適応型に置き換えます。

### Phase D: プロバイダーとモデル能力

Codex、Cursor、Claude の認証状態、モデル許可リスト、利用枠、実行能力を事前確認し、利用者が実行前に判断できるようにします。

### Phase E: GitHub 操作

差分・検証・レビューの承認後に commit、push、PR 作成を実装します。CI と PR 状態を表示し、操作を冪等にします。merge は保護ルールと監査を確認してから判断します。

### Phase F: 画像・アセット拡張

画像生成または外部アセットの要件、プレビュー、保存、レビュー、コスト、著作権、再生成を独立して追加します。

## 11. 未決定事項

実装に入る前に、次を人が決定します。

1. P2 の正式な対象タスクと、対象外にするタスク。
2. タスク全体の安全境界を設ける場合の既定値と、利用者が延長できる条件。
3. 初期の同時実行数（候補は2）と、メモリ・CPUによる抑制方法。
4. ブラウザ切断時に自律実行を継続するか（推奨: チェックポイントを保存して継続可能）。
5. Codex、Cursor、Claude で許可するモデル一覧と、認証・利用枠の表示方法。
6. 画像生成を P2 の成果物参照までにするか、P3 の生成実行まで含めるか。
7. アプリ内の commit・push・PR 作成をどこまで自動化するか。
8. アプリ内 merge を P2 に含めるか、GitHub への導線に留めるか。
9. GitHub 以外の CI・Git ホスティングを P2 で扱うか。
10. ログ、出力、成果物の保持期間と、利用者による削除・エクスポート方法。

## 12. 現在の実装との差分に関する注意

この要件は現行実装の完了報告ではありません。現行リポジトリには、固定のレビュー経路、ステップ予算、既存のタスク・承認・PR 画面がありますが、P2 の適応型フロー、複数タスク並列、要件整理の独立画面、モデル許可リスト表示、チェックポイント再開、条件付き検証がすべて実装済みであることを意味しません。

先にこの文書と `/p2-mock` の画面を人が確認し、用語と優先順位を決めます。その後に状態モデル、実行基盤、検証、Git 操作を順番に実装します。
